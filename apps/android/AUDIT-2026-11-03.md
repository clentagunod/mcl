## Findings requiring approval

### F01 — High: default receipt path permits overpayment and financial tampering

Evidence: [mobile receipt service](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/payments.ts:24), [shared payment service](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/services/payments.ts:18), [rules](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/firestore.rules:40), [backend switch](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/services/receipt-backend.ts:6).

The mobile service reads receipts before its transaction, then writes only the new receipt. Two devices can each see the same outstanding balance and submit different IDs without changing a shared document that forces the balance to be recomputed. Example: two receipts of 75 against an outstanding 100 can both commit. The web direct-write service does not perform this aggregate check. Direct-write rules validate individual receipts but do not enforce the outstanding total, so a modified authorized collector client can bypass the UI check altogether.

The transactional callable already advances the shared client document and reads receipts transactionally, but it is optional. The inspected APK asset uses the direct path, and the rules default to allowing direct receipts when the policy gate is absent. Current production settings were not queried.

Proposed fix: finish compatibility work, validate all writers against the callable, release compatible web/APK versions, then separately approve backend-only enforcement. Preserve legacy loan IDs and pending receipt IDs. Enabling the gate immediately would break older writers. This is a coordinated rollout, not a safe one-line flag change. [Firestore transaction isolation](https://firebase.google.com/docs/firestore/transaction-data-contention).

### F02 — High: a rejected callable receipt can permanently lock payment entry

Evidence: [pending receipt handling](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/PaymentDialog.tsx:44), [validation-only reservation release](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/PaymentDialog.tsx:60), [disabled pending fields](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/PaymentDialog.tsx:72).

Only the local PaymentValidationError class releases a reservation. Callable rejections arrive as Firebase functions errors, so a definitely rejected overpayment or below-minimum receipt remains reserved with its amount/date disabled. Reopening restores the same rejected payload and offers only another identical retry.

Reproduced with VITE_RECEIPT_BACKEND=callable-v1 and a mocked FAILED_PRECONDITION response. The invalid amount remained disabled and persisted after reopening. No customer data was accessed. Diagnostic: [audit-recovery.mjs](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/.tmp/audit-recovery.mjs).

Proposed fix: add safe rejection/reconciliation semantics and allow correction only after proving the reserved operation has not committed. Prevalidate common amount/date errors before reservation. Keep the original ID for uncertain transport errors, ambiguous failures, and previously committed operations. Do not solve this by deleting every reservation on any error.

### F03 — High: client deletion races payments and can partially erase the ledger

Evidence: [deleteClient](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/services/clients.ts:114), [mobile delete action](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/Clients.tsx:42), [rollout deletion limitation](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/docs/receipt-rollout.md:51).

Deletion reads payments once, deletes them in independent batches, and deletes the client last. A receipt arriving after the query can survive without its client. A failure after one successful batch can leave only part of the payment history. A concurrent renewal can also make later deletion fail after earlier destructive work. This is not one atomic operation.

Backend-only rules block legacy batch receipt deletion, which additionally breaks this existing workflow for clients whose receipts are returned by the query. An empty-client deletion racing a new receipt still needs explicit coordination.

Proposed fix: design coordinated deletion or archival with a client state that blocks new receipts/renewals, server-side authorization, durable progress, and retained audit evidence. Preserve the existing user-facing workflow only after its replacement is ready. Retention versus hard deletion is a business decision requiring approval.

### F04 — Medium: malformed existing amounts bypass the direct outstanding check

Evidence: [paid-total calculation](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/payments.ts:46).

Existing amounts are coerced with Number without finite/money validation. One malformed current-cycle amount turns paid and outstanding into NaN; the comparison against outstanding then fails open. A form already open when an invalid import arrives can still submit. The subscription converter's error banner does not fix the service boundary.

Reproduced: the valid-ledger control rejected 1000 against a loan of 100; adding one malformed existing amount allowed the same attempted receipt through the mocked write boundary. Diagnostic: [audit-direct.test.ts](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/.tmp/audit-direct.test.ts). This verifies the application validation defect, not a real Firestore write.

Proposed fix: validate every relevant server receipt before summing integer centavos; reject inconsistent data with a repair message. The callable already contains a stronger corresponding validation.

### F05 — Medium: correcting a renewed receipt rewrites its original entry time

Evidence: [direct correction write](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/payments.ts:53), [renewed-cycle rule](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/firestore.rules:115), [callable correction](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/functions/src/receipt.ts:105).

For renewed cycles, the direct Android correction replaces createdAt with a new server timestamp. That changes the apparent entry time of an existing payment and distorts recent-payment and collector-activity displays. The rule currently requires this timestamp behavior for renewed direct writes, so removing the client field alone would cause permission failures. Direct corrections/deletions also lack the callable's immutable before/after audit events.

Proposed fix: use the callable correction/audit path, preserving createdAt and the original collector while storing updatedAt/updatedBy separately. Coordinate rules and rollout; preserve old readers.

### F06 — Medium: device-transfer exclusions are missing for sensitive local state

Evidence: [manifest](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/src/main/AndroidManifest.xml:8), [data extraction XML](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/src/main/res/xml/data_extraction_rules.xml:6), [legacy backup XML](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/src/main/res/xml/backup_rules.xml:9).

allowBackup is false, but the extraction rules are starter templates and device-transfer exclusions are absent. Some manufacturers allow device-to-device transfer despite allowBackup=false. WebView authentication persistence and reserved receipt payloads therefore need an explicit transfer policy.

Proposed fix: explicitly exclude sensitive app storage domains for both backup formats and device transfer. Preserve on-device pending receipts; do not clear them on sign-out or startup. This affects transfer behavior, not ordinary payment storage. [Android backup behavior](https://developer.android.com/identity/data/autobackup), [Firebase default auth persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence).

### F07 — Medium: Gradle can reuse a bundle built with the wrong environment flag

Evidence: [bundleMobile inputs](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/build.gradle.kts:46), [mobile scripts](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/package.json:4), [Vite configuration](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/vite.config.mts:14).

Gradle tracks source and .env files, but not process VITE_* values or mobile/package.json. Changing VITE_RECEIPT_BACKEND in CI/the shell without changing tracked files can leave bundleMobile UP-TO-DATE and package the previous write path. Changes to the mobile build script are also omitted from its inputs. Generated assets are written into src/main and already have uncommitted changes.

Proposed fix: declare actual environment/build-script inputs and validate the resulting bundle's project and backend mode before release. Consider moving generated assets under build with proper source-set wiring in a separate, tested change. Do not replace the user's generated assets during this audit.

### F08 — Medium: dismissible busy forms combine with non-idempotent client creation

Evidence: [mobile modal dismissal](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/Modal.tsx:27), [client form](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/pages/clients/ClientFormModal.tsx:79), [confirmation dialog](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/components/ConfirmDialog.tsx:31), [client allocation](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/services/clients.ts:36).

The shared client/collector/confirmation forms disable their visible Cancel controls while busy, but pass an unrestricted onClose to the mobile modal. Its header, backdrop, and Escape handler still dismiss them during a save. The operation can commit after the UI is gone. Client creation has no durable operation ID across separate submissions, so retrying an uncertain completed create can allocate another client.

Proposed fix: prevent dismissal during in-flight mutations and give client creation an idempotency strategy before claiming safe retry. Treat account provisioning carefully: an interrupted account/profile operation also needs reconciliation rather than blind repetition.

### F09 — Medium: business dates depend on the phone's timezone

Evidence: [todayISO](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/lib/dates.ts:30), [mobile date validation](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/payments.ts:41), [server business day](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/functions/src/index.ts:13), [rules UTC+8 day](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/firestore.rules:77).

UI today and the direct validator use the device's local timezone; the callable uses Asia/Manila and rules use UTC+8. Near midnight, a phone set elsewhere can display a different collection day, reject a valid business-date receipt, or default to a date the server rejects.

Proposed fix: centralize a documented business-day function, align forms/defaults/validation with UTC+8, and test timezone and midnight boundaries. Do not migrate stored YYYY-MM-DD dates or reinterpret existing collection dates.

### F10 — Medium, conditional: old WebView providers can fail without a useful recovery screen

Evidence: [minSdk](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/build.gradle.kts:19), [bootstrap](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/main.tsx:12), [settings cloning](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/config/settings.ts:88), [preview observer](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/WebIndexCard.tsx:33).

Android API 24 is supported, but the app assumes modern JavaScript syntax and browser APIs such as structuredClone and ResizeObserver. ES2020 targeting does not supply missing browser API polyfills. There is no provider capability preflight. Also, the initial await import('./App') occurs before ErrorBoundary is mounted, with no rejection handler; a bootstrap failure can leave the root blank.

This is a compatibility gap inferred from code, not a crash reproduced on an old physical device.

Proposed fix: define the supported WebView capability baseline, show a native/update or bootstrap error screen, and provide narrowly scoped fallbacks where practical. Test the oldest supported provider and OS combination before changing minSdk. [Android WebView compatibility guidance](https://developer.android.com/develop/ui/views/layout/webapps/jetpack-webkit-overview).

### F12 — Medium scalability limitation: pagination does not reduce database reads

Evidence: [collector feeds](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/CollectorData.tsx:18), [shared data provider](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/context/DataProvider.tsx:18), [full-query subscription](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/web/src/services/subscribe.ts:18), [per-save receipt query](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/payments.ts:24).

Every session loads the full clients/payments/holidays collections, and each snapshot is remapped in full. Visible pagination only limits rendered cards. Payment validation fetches the selected client's entire receipt history, including old cycles; the callable also scans all receipts for that client before filtering by cycle. Read cost, memory use, and work grow with retained history.

This is a scaling limitation, not a measured startup/ANR regression.

Proposed fix: measure realistic history sizes, separate recent/history queries, group or memoize calculations where useful, and design server-owned balances or compatible cycle queries. Preserve full financial totals and legacy initial receipts; simply adding a query limit would silently make balances wrong. Collector access currently covers all clients and receipts by policy; narrowing this to assignments would be a separate product/security decision.

### F13 — Low: Android Back does not dismiss web dialogs

Evidence: [native Back handler](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/app/src/main/java/com/mcl/mcllendingapp/MainActivity.kt:37), [modal handlers](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/Modal.tsx:27).

Dialogs are React state/portals rather than browser history entries. The Activity only goes back in browser history, and the modal only handles Escape. Hardware/predictive Back can leave the screen or app while a dialog is open instead of dismissing it. Unsaved drafts can be lost.

Proposed fix: coordinate the topmost dialog with the Android Back flow, honor busy states, preserve pending receipts, and test keyboard/IME Back ordering. Avoid adding a broad privileged JavaScript bridge solely for this.

### F15 — Low: asynchronously loaded settings can start in a misleading conflict state

Evidence: [settings draft initialization](C:/Users/Cloy/Documents/Programming/Monorepo/mcl/apps/android/mobile/src/Settings.tsx:14).

## Additional review notes

- No embedded service-account private key, signing password, or OAuth secret was identified in the inspected source and asset checks. Excluded local files and Git history remain outside that statement. The Firebase public configuration/API key in the bundle is expected, not itself a credential leak. Access depends on rules and appropriate API restrictions. [Firebase API-key guidance](https://firebase.google.com/docs/projects/api-keys).
- The launcher uses HTTPS assets, blocks cleartext and file/content access, rejects mixed content, limits main-frame navigation, disables release WebView debugging, and has no native JavaScript interface. No TLS-error bypass was found. Print data is escaped and the index iframe disallows scripts.
- Auth waits for server profile confirmation; normal payment success waits for server acknowledgement; reserved receipts retain stable IDs for uncertain outcomes. Those safeguards should be preserved.
- ANR risk: no proven application-owned blocking main-thread I/O or off-main mutation of an attached View was found in the inspected Kotlin paths. Firebase Task.await suspends rather than blocking. Native in-memory mapping/sorting has no measured ANR proof; WebView startup and renderer responsiveness require device profiling before assigning an ANR finding.
- Retained native collector code is not the launcher. It still has legacy direct-write behavior and memory-only pending form IDs. Do not reactivate it as an alternative payment UI without upgrading recovery/backend behavior. Native Firebase/Compose dependency removal is a separate size-maintenance option requiring dependency and release verification.
- Release assembly is not distribution approval. No release signing configuration was present in the inspected build file, versionCode remains 1, and signing-key custody/update compatibility were not verified.
- The current Android instrumentation test checks only package identity. Add meaningful on-device coverage for Back/IME, process death, renderer recovery, retained receipt IDs, revocation, and the oldest supported WebView.
- App lock/MFA, screenshot/recents privacy, App Check/rate limiting, audit retention, monitoring, and backup/restore policy need product/operational decisions. They are hardening options, not proven exploits or permission to change current access behavior.
- Existing rollout documentation already acknowledges some financial and scale limitations. They remain present in the current default path; documenting them does not enforce the invariants.

## Proposed approval boundaries

1. **Compatibility-preserving code fixes:** prepare focused changes for receipt recovery and validation, modal/busy handling, explicit sensitive-data transfer exclusions, build input tracking, bootstrap recovery, Back/offline handling, settings initialization, and search. Keep collection/document shapes, existing receipt IDs, loan-cycle semantics, and feature-flag defaults stable. Where a shared contract is needed, review and test web and Android together.
2. **Coordinated financial changes:** separately approve authoritative receipt enforcement and coordinated client deletion/audit behavior. Test mixed old/new writers and resolve the deletion workflow before enforcing backend-only rules. Do not change live policy, deploy, migrate, or retire older APKs as part of an ordinary local fix.
3. **Dependency and scaling maintenance:** triage exact advisory paths and benchmark data volumes before selecting upgrades or query/aggregate changes. Validate web, functions, mobile, and Android release behavior after each bounded change.

Before merging any approved shared fix, rerun relevant unit/emulator/browser/device checks against test data. No change can be guaranteed risk-free; preservation of current behavior should be demonstrated with targeted regression tests and a reviewable diff.
